# Project 2 — Requirements

## Goal
Build a complete role-based information management system with a web interface and cross-platform mobile app (Android and iOS). This project must be developed independently from Project 1.

## Confirmed functional requirements
- Web application and mobile app with a shared backend API.
- Database storing user accounts, roles, application records, audit events, and backup metadata.
- Four seeded demonstration accounts, each with a different role.
- Separate administrator and ordinary-user interfaces.
- Administrator-only menus and server-enforced authorization.
- Multi-factor authentication (2FA).
- Password hashing with a unique salt per password and a separately stored pepper.
- Create, view, update, and delete application records according to role permissions.
- Deleted users must no longer be able to sign in or appear in active-user listings.
- Several demonstration records must be entered.
- Reports presented in separate tabs.
- System status/current-state view.
- Backup history and a demonstrated restore process.
- A configuration restore point must restore configuration only and must not alter application records.
- Create an AWS account and deploy the system.
- Generate an OpenPGP public/private key pair using Kleopatra and document safe handling.
- Provide test evidence and documentation for the demonstration.

## Proposed role model
1. **Super Admin** — manage system configuration, administrators, roles, users, records, reports, and backup settings.
2. **Administrator** — manage users and records, and access reports and backup operations allowed by policy.
3. **Manager** — manage permitted records and view reports; no system-wide security configuration.
4. **Ordinary User** — use permitted user functions and access only records they are authorized to see.

All permissions must be checked on the server/API. Hiding a menu alone is not security.

## Security requirements
- Never store or display plaintext passwords.
- Use PHP's password hashing and verification APIs with a unique salt generated by the library; do not invent a custom hashing algorithm.
- Keep the pepper outside the database and source control, supplied through environment/secrets configuration.
- Do not include passwords, OTPs, private keys, access tokens, or production secrets in GitHub.
- Use secure sessions/tokens, input validation, parameterized database queries, rate limits, and audit logging.
- A deleted account must be disabled immediately and removed from active listings; permanent deletion must also respect audit/integrity requirements.

## Backup and restore acceptance test
1. Add identifiable test records and record their count/IDs.
2. Save a configuration restore point.
3. Change a configuration setting.
4. Restore the configuration restore point.
5. Verify the configuration changed back.
6. Verify the application records, record IDs, and record count did not change.
7. Keep an audit event for backup/restore activity.

Record-data backups, if implemented, must be a separate operation from configuration-only restore points.

## Reporting tabs (proposed)
- Dashboard / system status
- Users and roles
- Application records
- Security and audit events
- Backup history and restore tests

A user report may show usernames, roles, status, and password-security metadata only. It must never expose actual passwords, password hashes, salts, or the pepper.

## Acceptance criteria
- The web app and mobile app authenticate against the same backend.
- All four test roles demonstrate different permissions.
- Unauthorized API requests are rejected even if manually submitted.
- 2FA is required according to the configured policy.
- Password storage demonstrates salted hashing and separately managed pepper protection.
- User deletion prevents further login and removes the account from active-user results.
- Records can be entered and reported.
- Configuration restore does not modify records.
- Kleopatra key generation and public/private key handling are demonstrated.
- Deployment is reachable and tested, with no secrets committed to Git.
